## Записи по пробам
### Инфраструктура
- Пересборка шейдеров ggml-vulkan: `touch mul_mm.comp; cmake --build build --target ggml-vulkan -j8` = **15 с**. Потом перелинковать `bench3`:
  `g++ -O2 -std=c++17 -I$S/ggml/include bench3.cpp -o bench3 $B/ggml/src/ggml-vulkan/libggml-vulkan.a $B/ggml/src/libggml.a $B/ggml/src/libggml-cpu.a $B/ggml/src/libggml-base.a -fopenmp -lpthread -ldl -lm -lvulkan`
- Используемый вариант: DATA_A_F16, f16 accumulators (ACC_TYPEV2 = f16vec2), cache_a/cache_b = f16vec4 (4 значения k), dot_product_v2.

### Пункт 1: откуда v_xor_b32_sdwa (причина найдена)
Сырой дамп: тройки `v_xor_b32_sdwa` обменивают половинки двух регистров (XOR-swap, dst_sel/src_sel WORD_0/WORD_1).
Причина: LDS хранит A как (k, k+1) для одной строки; а dot_product_v2 считает две строки (2cr, 2cr+1) в sums.xy и для v_pk_fma ему нужна пара
(a[строка 2cr][k], a[строка 2cr+1][k]) -> транспонирование 2x2 между регистрами. Лечение: хранить A в LDS парами по строкам (row-pair, k).
Статус: идея; реализуется в шейдере (mul_mm.comp + load_a_to_shmem в mul_mm_funcs.glsl).

### Пункт 6: активации f16 (сделано)
bench3 с XF16=1 (B в f16): 1379/1348 и 1351/1343 против f32 1252/1255 и 1241/1242 -> **+9%**. В README это же (+5-12%) для Anima, там cast слит в norm.
Для Kromoss (moss_image.hpp) входы linear идут в f32 (RMSNorm -> modulation -> linear). TODO: cast в f16 для qkv, proj.o, ffn_up_gate, ffn_down; оценка выигрыша на шаге ~5% (минус проход cast, если не слит).

### Пункт 1: row-pair layout (сделано, 3 итерации)
1. Первая версия (запись половинок buf_a[..].x/.y по чётности строки): xor исчезли, но цикл раздулся до 1817 инструкций (ветвление по чётности, s_cbranch_execz x63, 64 ds_write_b16), скорость -12% (1075-1110).
2. Вторая (поток грузит две соседние строки и пишет пары f16vec2): сначала ошибка 7e3 (неверная индексация FLOAT_TYPEV8: это пара vec4, не 8 скаляров), исправлено.
3. Итог: правильно (err 8.3e-4), f32-B: 1151-1156 против 1226-1242 (-7%); f16-B: ~1365 против ~1318 (+3-4%, 4 чередующихся прогона).
   Дамп f16-B: цикл 1418 против 1512 инструкций, VGPR 112 против 128 (всё ещё 2 волны), ds_read 160 = 160, ds_write 16 = 16, waitcnt 118 против 144.
Вывод: выигрыш есть только вместе с f16-активациями (пункт 6). Шейдер общий для всех моделей: чтобы не замедлить f32-B, нужно ограничить ROWPAIR вариантом с B=f16 (флаг от генератора).

### Пункт 5: k=8192 (в работе)
Реальные формы Kromoss, f16-B, orig (повторы в разном порядке): qkv 9216x3072: 1350-1394; o 3072x3072: 1334-1396; up_gate 16384x3072: 1140-1266 (шумит); **down 3072x8192: 1015-1042**.
Перебор плиток при k=8192 (rowpair, f16-B; селектор выбирает большую при k>=4096): default L 128x128/4 волны 1059-1088; force m (64x64) **664**; L 128x256 805; L 256x128 683-693; L 128x64 737-748; L 64x128 938-949; L 128x128/2 волны 701-704. Большая плитка по умолчанию лучшая.
Скан K (M=3072,N=1536, f16-B): 3072: 1417-1431; 4096: 1405-1434; 4160: 1030 (K%128!=0 -> невыровненный шейдер); 6144: 1238-1254; 8000: 972-1012 (невыровненный); **8192: 1081**; 8256: 1019-1029 (невыровненный); **8320: 1241-1248**.
=> при выровненном K скорость на 8192 (шаг строки ровно 16 КБ) ниже, чем на 8320/6144, на ~13-15%. K=8320 = K=8192 + нулевой добавок: с учётом лишних 1,6% работы эффективно ~1229 против 1082 (**+13%**). Гипотеза: совпадение каналов/наборов кэша из-за шага 2^14 байт.
Тест view с шагом (PAD=8..256): 1005-1013, т.к. ggml-vulkan шлёт в шейдер stride_a = ne10 и копирует non-contiguous src0 (строка 6742 ggml-vulkan.cpp) -> тест некорректен для этой гипотезы.
Следующая проба: сдвиг старта цикла по K для каждой рабочей группы (ROTK), чтобы параллельные группы читали разные участки K.

### Пункт 5: результаты (ROTK)
Сдвиг старта цикла по K у каждой рабочей группы (ROTK в mul_mm.comp): `rot = (ir*ROT_A + ic*ROT_B) % nkb`, только если K%BK==0 и stride_a % 8192 == 0.
- ROT 7,13 (всегда): k=8192 1124 (+4%), но k=3072 1257 (-10%: группы перестали делить L2 по B) -> нужно ограничение по шагу строки (добавлено).
- Перебор ROT_A при ROT_B=0 (k=8192, база 1081): 1->1094, 2->1118, 3->1132, **4->1150-1154**, 5->1139-1145, 6->1126-1134, 8->1090-1114, 16->1035. ROT_B 1/4/12/16 с A=4 не лучше (1133-1145). **Выбрано ROT_A=4, ROT_B=0.**
- Итог по реальным формам (f16-B, orig / текущий шейдер rowpair+ROTK): 3072x3072 1374/1370; 9216x3072 1348/1366; 16384x3072 1258/1260; **3072x8192 1033/1144 (+10,7%)**; 3072x8192, N=1636 1019/1132 (+11%). Ошибка 8e-4..1e-3 как у базы.
- Rowpair отдельно (+3-4% в первом замере) в этом прогоне на k=3072 не виден (в пределах шума 0-2%): оценка выигрыша rowpair уточнить сквозным замером.
- Не пробовал: split-K (при 72-288 плитках на 7 CU вряд ли поможет), раскладка запуска групп (swizzle ir/ic).
- Вес на модель: матмулы k=8192 = 22% FLOPs; +10% на них = ~+2% по всем матмулам блока.

### Пункт 3: веса плитками (сделано, ГЛАВНЫЙ РЕЗУЛЬТАТ)
**Поправка к раннему выводу:** косвенный тест BK=32 (-5%) говорил, что coalescing не узкое место. Это было неверно: прямой тест показал большой выигрыш.
Реализация: TILEDA в mul_mm_funcs.glsl (aligned-ветка ROWPAIR): адрес A = ((ir*nkb + kb)*BM + row)*BK + k, то есть каждая плитка BMxBK лежит подряд (4 КБ для 64x32). bench_tiled.cpp переставляет веса на хосте (TILED=1, TILE_BM).
Результаты (текущий шейдер rowpair+ROTK; чередование cur/tiled, 2 раунда, f16-B, ошибка прежняя):
| форма | cur | tiled | прирост |
|---|---|---|---|
| 3072x3072x1536 | 1338-1414 | 1458-1489 | +4..+9% |
| 9216x3072x1536 | 1372-1439 | 1471-1583 | +6..+9% |
| 16384x3072x1536 | 1235-1265 | 1393-1482 | +12..+15% |
| 3072x8192x1536 (BM=128) | 1119-1158 | 1494-1551 | **+32..+35%** |
| 3072x8192x1636 | 1134-1143 | 1485-1527 | **+31..+34%** |
Оценка по FLOPs блока (qkv 25%, o 8%, up_gate 45%, down 22%): время матмулов -13% только от раскладки; вместе с f16-B (+9%) около -20%.
Идея интеграции: фиксированная раскладка плиток 64 строки x 32 k для всех f16-весов с K%32==0, M%64==0; шейдер считает адрес для любой строки (ir*BM+col): tile=(row/64)*nkb+kb, off=(row%64)*BK+k, поэтому подходят и плитки BM=64, и BM=128.
Нужно: (a) переупаковка при загрузке весов (sd.cpp), (b) флаг на тензоре (ggml tensor flags), (c) вариант пайплайна TILEDA в ggml-vulkan (генератор шейдеров + выбор), (d) сквозной тест Kromoss.

## ИНТЕГРАЦИЯ плиток f16 (начата 2026-11-01)
Решение: пункт 3 интегрируется для f16-весов Anima (Q6_K Kromoss не нужно: там матмул уже ~1450).
Что сделано в sd-src (оставлено в дереве, это запрошенная функция; бэкапы оригиналов в perf-notes/backup_orig/):
- `ggml/include/ggml.h`: флаг тензора `GGML_TENSOR_FLAG_TILED_F16 = 32`.
- `ggml/include/ggml-vulkan.h` + `ggml-vulkan.cpp`: `bool ggml_backend_vk_tile_f16_weight(ggml_tensor*)`: читает вес с GPU, раскладывает плитками 64 строки x 32 k (tile-major: (блок строк 64)*(K/32)+блок k), пишет обратно, ставит флаг. Условия: F16, 2D, contiguous, K%128==0, M%64==0, не view.
- `ggml-vulkan.cpp`: бит `MM_EPI_TILED = 4` в push-константе `epi`; в `ggml_vk_mul_mat_q_f16` для тензора с флагом: ассерт (aligned, нет dequant/non-contig, ne02=ne03=1), split-K отключён; в трёх mat-vec путях ассерт "tiled weight reached mat-vec path".
- `vulkan-shaders/mul_mm_funcs.glsl`: в aligned-ветках загрузки A (LOAD_VEC_A 8 и 4, только DATA_A_F16 без MUL_MAT_ID) адрес считается из тайлов, если `p.epi & 4`. Rowpair/ROTK/TILEDA-экспериментальные варианты НЕ включены (rowpair давал -7% на f32-B и 0-4% на f16-B).
- `src/model_manager.cpp`: после загрузки весов в params backend, если `SD_VK_TILE=1` и нет LoRA, вызывается API для весов блоков Anima: self_attn q/k/v/output_proj, cross_attn q_proj/output_proj, mlp layer1/layer2 (не трогаются adaln_modulation (N=1), cross_attn k/v_proj (мало токенов), llm_adapter, embedder'ы). Слабый символ: сборки без Vulkan линкуются. LoRA на тайловых весах: явная ошибка.

### Прототип: фрагменты весов A сразу в регистры, минуя LDS (2026-11-01, отрицательный)
Идея: веса лежат плитками, поэтому кусок каждого потока можно переложить заранее в порядок "[i][группа строк потока][4 строки][4 k]" (32 байта подряд на поток на шаг i) и читать прямо в cache_a, без записи в LDS и чтений A из LDS (шейдер FRAGA, хост-раскладка bench_frag).
Результаты (3072x3072x1536 / 3072x8192x1536, f16-B, GFLOPS; база = встроенные плитки через API: 1347-1395 / 1320-1378):
| вариант | 3072x3072 | 3072x8192 |
|---|---|---|
| A в регистры, без предвыборки | 1032-1097 (-22%) | 959-993 (-28%) |
| + предвыборка следующего фрагмента | 1078-1095 (-20%) | 1010-1043 (-24%) |
| все 8 фрагментов блока загружаются в начале блока (64 лишних VGPR) | 836-860 (-38%) | 681 (-50%) |
Все варианты считают правильно (ошибка та же 8.3e-4 / 8.1e-4).
Причины (по дампу и логике, не все проверены): задержка глобальной памяти (сотни тактов) вместо LDS (десятки) торчит в цикле при двух волнах на SIMD; в варианте с предвыборкой цикл по i перестал разворачиваться (в шейдере 128 FMA вместо 1024: переменные fa01/fa23 переходят между итерациями), поэтому он нечестен; вариант с пачкой загрузок раздувает регистры (>128) и оставляет одну волну на SIMD.
Вывод: идея не работает на этой карте в рамках GLSL; закрыто. Чтобы дать ей честный шанс, нужен ручной контроль развёртки и расписания (ассемблер/SPIR-V), чего здесь нет.
Измерения формы (отдельный замер того же дня): эффективность матмула плоская по всем формам и ширинам, ~1300-1375 GFLOPS (N=768..6144; QKV слитые 1321-1342 против 1289-1304 отдельной Q: +3%).
Исходники возвращены к встроенной версии (дерево == закоммиченный патч).

### Причина потерь у матмулов Anima и исправление (2026-11-01)
Профиль шага Anima 2B (GGML_VK_PERF_LOGGER) показал, что "37% шага" это матмулы со слитым эпилогом (output_proj k=2048: 56 вызовов, MLP2 k=8192: 28 вызовов), идущие на 1180-1245 GFLOPS вместо 1390 у обычных. Отладочная печать (пайплайн, тип B, эпилог) по каждому матмулу:
- output_proj: B = f32 (выход flash attention), пайплайн matmul_f16_f32_f16acc_aligned_1; f32-B ~ -7%, эпилог ~ -3%. Перевод B в f16 отдельным проходом выиграл бы ~0,3% шага: не исправляется.
- MLP2: большая плитка 128x128 на 4 волны; эпилог (вынос затвора, vec2 для остатка) ничего не дал (проверено).
- Микробенчмарк на k=8192 ВВОДИЛ В ЗАБЛУЖДЕНИЕ: его буферы лежат по идеально выровненным адресам, поэтому патология шага 16 КБ и "+25-35% от плиток на k=8192" в реальном графе не проявились (реальный k=8192 без плиток уже ~1050-1150, с плитками ~1180). Заслуга плиток весов в реальном графе: MLP1 +13% (1225 -> 1386), k=2048 +3%. Бенчмарки плиток (таблица выше) верны для своих условий, но переносить их на график нельзя без проверки профилем.
Нашёлся настоящий резерв: размер рабочей группы. Профиль реального графа (шаг, мс / GFLOPS plain k2048, MLP1, GR2048, GR8192):

| 128x64, 2 волны (BLOCK 128) | 4663 | 1391 | 1404 | 1243 | 1323 |
| 64x128, 2 волны | 4564-4615 | 1465 | 1499 | 1270 | 1238-1288 |

Выбрана плитка {128,64,128,16,32,128,1,4,4,1,64} (BLOCK 128, BM 64, BN 128, WM 32, WN 128), wg_denoms {64,128}.
Включение: только в процессе с SD_VK_TILE=1 на не-coopmat GCN; селектор берёт её при m>=512, n>=512 и отходе от кратности 128 по n не более 6% (иначе прежняя логика). Остальные процессы не меняются.
